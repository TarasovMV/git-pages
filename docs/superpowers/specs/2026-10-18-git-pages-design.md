# git-pages — дизайн-спека

Дата: 2026-10-18
Статус: согласован с пользователем (вариант 1 + галерея + файл-страницы в общих папках)

## Цель

Личное хранилище веб-страниц (HTML-артефактов) в публичном репозитории GitHub.
Каждая страница доступна по живому URL через GitHub Pages и идентифицируется
ключом (= путь). Добавление, редактирование и удаление страниц выполняет агент
ZCode через пользовательский скилл `git-pages`. История изменений каждой
страницы — в git.

## Зафиксированные решения

| Вопрос | Решение |
|---|---|
| Хостинг | GitHub Pages, репозиторий публичный: `TarasovMV/git-pages` |
| Формат страницы | Один самодостаточный HTML-файл (HTML+CSS+JS внутри) |
| Ключ / URL | Ключ = относительный путь без расширения; URL вычисляется из ключа |
| Реестр | Нет манифеста; структура файлов — единственный источник правды |
| Галерея | `index.html` в корне, генерируется скриптом после каждой операции |
| Инструмент | Пользовательский скилл ZCode (не MCP, не отдельный CLI) |
| Метаданные | HTML-комментарий `page-meta` в шапке файла страницы |
| Даты | Из `git log` по файлу (не из метаданных) |

## Архитектура

Три компонента, без сервера и runtime-зависимостей:

1. **Репозиторий** — хранит страницы, ассеты и историю (git).
2. **Скрипт** `tools/rebuild_index.py` — вся логика проекта: сканирует `pages/`,
   генерирует галерею. Только stdlib (pathlib, re, datetime, subprocess, html).
3. **Скилл** `git-pages` — инструкции для агента ZCode: протоколы операций.

### Структура репозитория

```
git-pages/
├── .nojekyll              ← отключает Jekyll: чистый статический хостинг
├── index.html             ← генерируется скриптом; руками не редактировать
├── README.md              ← описание системы для GitHub
├── tools/
│   └── rebuild_index.py
├── docs/
│   └── superpowers/specs/...
└── pages/
    ├── shagal-electricity/
    │   ├── index.html     ← ключ: shagal-electricity
    │   ├── panel.html     ← ключ: shagal-electricity/panel
    │   └── data.json      ← не .html → ассет, не страница
    └── color-picker/
        └── index.html     ← ключ: color-picker
```

`.nojekyll` кладём сразу: все страницы — чистый статический HTML, Jekyll не
нужен; заодно GitHub Pages отдаёт `foo.html` по адресу `/foo` без расширения.

### Ключи, файлы, URL

**Ключ** — от 1 до 4 сегментов `[a-z0-9][a-z0-9-]*`, разделитель `/`.
Примеры: `color-picker`, `shagal-electricity`, `shagal-electricity/panel`.

**Разрешение ключа → файл** (детерминированное, в порядке приоритета):

1. `pages/<ключ>/index.html` — папка-страница
2. `pages/<ключ>.html` — файл-страница

Путь не может быть одновременно папкой и файлом, поэтому коллизий между
ключами нет. Если существуют оба варианта (папка `pages/a/` и файл
`pages/a.html`), побеждает правило 1; файл `a.html` при этом остаётся
достижим по URL `/pages/a.html`, но как страница не регистрируется.

**URL** (база: `https://tarasovmv.github.io/git-pages`):

- папка-страница: `/pages/<ключ>/` (со слэшем)
- файл-страница: `/pages/<ключ>` (без расширения, благодаря `.nojekyll`)

### Метаданные страниц

Необязательный HTML-комментарий первым блоком в `<head>` (или первым в файле):

```html
<!-- page-meta
title: Цветовой пикер
description: Подбор палитры
-->
```

- нет `page-meta` → заголовком в галерее становится ключ, описание пустое
- даты создания/обновления скрипт берёт из `git log` по файлу, в метаданных
  они не хранятся

### Галерея (index.html)

- адаптивная сетка карточек: заголовок, ключ, описание, дата обновления,
  ссылка на живую страницу
- сортировка: по дате обновления (свежие сверху), затем по ключу
- вывод детерминированный (устойчивая сортировка) — повторная генерация даёт
  байт-в-байт тот же файл; это же решает конфликты в index.html
- никаких внешних зависимостей: инлайн-CSS, системные шрифты

### Скрипт tools/rebuild_index.py

- запуск из корня репо: `python tools/rebuild_index.py`
- находит все `**/*.html` под `pages/`, вычисляет ключ и вид (папка/файл);
  коллизии ключей (есть и `pages/a/`, и `pages/a.html`) разрешаются в пользу
  папки — затенённый файл в галерею не попадает
- режим `--list`: печатает `ключ | заголовок | дата обновления` по тем же
  данным — детерминированный источник для операции `list` скилла
- парсит `page-meta` (регэкспом по первому подходящему комментарию)
- даты: `git log -1 --format=%cs -- <файл>` (обновление) и
  `git log --diff-filter=A --format=%cs -- <файл>` (создание)
- рендерит `index.html` из шаблона внутри скрипта
- коды выхода: 0 — ок; 1 — нет папки `pages/`; 2 — git недоступен
- страницы без единого коммита (ещё не закоммичены) попадают в галерею с
  датой «сегодня»

### Скилл git-pages (пользовательский, ZCode)

Устанавливается на уровне пользователя ZCode (виден во всех проектах; точное
место установки уточняется по конфигурации ZCode при реализации). Знает
фиксированный путь локального клона:
`C:\Users\taras\Documents\Projects\git-pages`.

Операции:

- `setup` (один раз): установка gh, `gh auth login`, включение Pages
- `add <ключ>`: создать страницу (контент генерирует агент по просьбе
  пользователя), с `page-meta`
- `update <ключ>`: перечитать файл, внести правки (агент), сохранить
- `delete <ключ>`: удалить файл (и опустевшую папку)
- `list`: перечень страниц с заголовками и датами
- `open <ключ>`: открыть живой URL в браузере (`start <url>`)

Протокол любой изменяющей операции:

1. `git pull --ff-only` (синхронизироваться)
2. применить изменение (файл по разрешению ключа)
3. `python tools/rebuild_index.py`
4. `git add -A && git commit` — сообщения: `page: add <ключ>`,
   `page: update <ключ>`, `page: delete <ключ>`
5. `git push`
6. проверить живой URL: поллинг `curl` до 90 секунд (деплой Pages ~минута);
   при таймауте — честно сообщить, что деплой задерживается

Жёсткие правила для агента: не редактировать `index.html` вручную; валидировать
ключ до любых действий; при невозможности безопасно продолжить — стоп и вопрос
пользователю.

### Первичная настройка (setup, один раз)

1. `winget install GitHub.cli`, затем `gh auth login`
2. `git init` и первый коммит (спека) выполняются при фиксации дизайна;
   setup создаёт структуру (`README.md`, `.nojekyll`, `tools/`, `pages/`)
   и коммитит её
3. `gh repo create TarasovMV/git-pages --public --source . --push`
4. Включить Pages (ветка main, корень):
   `gh api -X POST repos/TarasovMV/git-pages/pages -f "source[branch]=main" -f "source[path]=/"`

## Обработка ошибок

| Ситуация | Поведение |
|---|---|
| Невалидный ключ (регистр, подчёркивания, кириллица, >4 сегментов) | Отказ + предложение валидного варианта (например, транслит) |
| `add` на существующий ключ | Отказ: «это update» |
| `update`/`delete` несуществующего ключа | Отказ + показать `list` |
| Грязное рабочее дерево перед операцией | Стоп и вопрос пользователю |
| Push отклонён | `git pull --rebase`; конфликт только в `index.html` → перегенерировать скриптом; конфликт в странице → стоп и вопрос |
| Pages не ответил за 90 с | Сообщить о задержке деплоя, дать URL для ручной проверки |
| Скрипт вернул 1/2 | Разобраться (нет pages/, нет git), не пушить вслепую |

## Тестирование

**Юнит-тесты** (unittest, stdlib), рядом со скриптом (`tools/tests/`):

- валидация ключей: валидные/невалидные, глубина, регистр
- разрешение ключа → файл (папка приоритетнее файла)
- парсер `page-meta`: есть/нет/многострочные значения/пустые поля
- генерация index: содержит все страницы, сортировка, детерминированность
  (двойной запуск → идентичный файл)

**Приёмочный тест** (полная цепочка, на реальном репо после setup):

1. `add _self-test/hello` (простая страница) → локальный предпросмотр
   `python -m http.server` в корне репо → проверить рендер страницы и галереи
2. push → поллинг живого URL до 200 → проверить, что URL файл-страницы
   работает без расширения
3. `update _self-test/hello` → push → проверить изменение
4. `delete _self-test/hello` → push → проверить 404 и исчезновение из галереи

## Не-цели (YAGNI)

Поиск и теги в галерее, приватность/доступ, MCP-сервер, сборка из нескольких
файлов (бандлеры), аналитика, комментарии, темы оформления галереи.
